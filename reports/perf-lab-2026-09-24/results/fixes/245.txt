rmp #245 — RequestID: batched crypto/rand reads + allocation rewrite
Machine: AMD Ryzen 9 5900HX, 16 logical CPUs, Linux 6.8.0-139-generic, go1.27.0 (module go 1.26)
Before = git HEAD content (rand.Read(16 bytes) per request; context.WithValue; hex.EncodeToString;
         non-canonical "X-Request-ID" literal passed to Header.Get/Set on every call).
After  = (1) batching (sync.Pool of 4KiB buffers, 256 IDs/refill; safe math/rand/v2 fallback only
         on a genuine crypto/rand.Read error) PLUS (2) the coordinator-requested follow-up:
         precomputed canonical header-key constant + direct map access (no per-call
         CanonicalMIMEHeaderKey), and a fused *requestIDCtx (embeds context.Context, overrides
         Value only for requestIDKey{}) that carries the context node, the hex digit buffer
         (unsafe.String-aliased, no copy), AND the response header's []string backing array
         in ONE allocation — replacing context.WithValue + interface-boxing + hex.EncodeToString
         + the header-value slice with a single allocation. r.WithContext's *http.Request copy
         is kept (unavoidable for a stdlib middleware, per instruction).

== FINAL CALL on the AC ("RequestIDParallel ns/op at cpu=16 improves >=2x vs baseline") ==
- cpu=1:  ~4.7x   (comfortably exceeds target)
- cpu=4:  ~2.8x   (comfortably exceeds target)
- cpu=16: ~1.92-1.98x across two independent, order-flip-controlled trials (pooled 1.95x)
          — a real, reproducible, but SHORT-of-2x result at the highest core count.

Every allocation removable within request_id.go's own scope has been removed: allocs/op is
down to 2, the theoretical floor for this design —
  (1) ONE fused allocation for the context node + hex-digit buffer + header-value backing array
  (2) r.WithContext's *http.Request copy, which the coordinator's instruction explicitly
      requires keeping ("unavoidable for a stdlib middleware — keep it").
CPU-profile evidence shows net/http.(*Request).WithContext itself (stdlib, out of scope) is now
the single largest cost (37% cumulative), with its own GC write-barrier overhead close behind
(~18%) — both structural properties of copying *http.Request, not of anything left in
request_id.go. No further allocation exists in this middleware to remove without violating the
"keep r.WithContext" instruction or changing observable behaviour (header/context/spec
semantics), so 1.92-1.98x at cpu=16 is reported as the achieved, evidence-backed result — short
of the literal 2x AC by a small, reproducible margin, not a measurement artifact.
