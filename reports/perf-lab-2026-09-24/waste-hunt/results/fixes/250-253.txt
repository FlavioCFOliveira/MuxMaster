WH-10 / #248 / Cached redirect handler + byte-identical direct write —
FOLLOW-UP FIX (2026-09-24, this task): the WH-10 cache above caused a
regression on BenchmarkParallelRedirectTrailingSlash (+17.35% ns/op, +30.77%
B/op, vs an 8->4 allocs/op improvement) that violated task #248's acceptance
criterion (allocs/op reduced AND ns/op improves at cpu=16, serial benches
must not regress). Root-caused and fixed; see mux.go doc comments on
redirectCtx/redirectBundle/serveRedirect (Opt R3/R4/R5) for the full
rationale. Root cause and fix summary:

  CAUSE: serveRedirect's middleware-present path carried the per-request
  redirect target/code to the cached, reused handler (lazyRedirect) via
  `context.WithValue(r.Context(), redirectCtxKey{}, redirectTarget{...})`
  followed by `r.WithContext(ctx)`. Under Go's interface-boxing rules this is
  THREE allocations per redirect: (1) the *context.valueCtx node itself, (2)
  a heap-boxed copy of the 24-byte redirectTarget value stored in valueCtx's
  `val any` field (too large to fit an interface's single data word, so the
  runtime heap-copies it), and (3) the cloned *http.Request from
  r.WithContext. cpuprofile evidence (pprof -top on a -cpuprofile of the
  parallel benchmark) showed GC write-barrier bookkeeping
  (runtime.bulkBarrierPreWrite / wbBufFlush1 / wbBuf.get2, ~13.5% cumulative)
  and mallocgc (~21-25% cumulative) dominating the sample — three
  separately-boxed heap objects under high parallel allocation churn (16
  goroutines) cost more wall-clock time than the N=5 short-lived middleware
  closures the WH-10 cache was designed to eliminate.

  FIX: (Opt R4) replaced the two calls with a single fused allocation —
  redirectBundle{ redirectCtx; http.Request } — modeled exactly on the
  existing reqBundle1/reqBundle2 pattern in params.go (Opt O12/O13):
  redirectCtx embeds context.Context directly and stores the 24-byte
  redirectTarget as a plain, unboxed struct field (no interface boxing), and
  the *http.Request copy is fused into the SAME allocation via the existing
  setReqCtxUnsafe/getReqCtxUnsafe unsafe-offset helpers (params.go) instead
  of r.WithContext's separate allocation. redirectTargetFrom mirrors
  routeCtxParams's fast/slow-path split: a direct `ctx.(*redirectCtx)` type
  assertion (no allocation) in the common case, falling back to the generic
  ctx.Value(redirectCtxKey{}) traversal only if a Use()-registered
  middleware has wrapped the context further before the cached handler
  runs. (Opt R3) writeRedirect's GET-body construction was also collapsing
  two string concatenations (`body := ...; body+"\n"`) into one — a second,
  unrelated one-line waste found while investigating. (Opt R5) Location/
  Content-Type headers are now set via direct map assignment
  (`h["Location"] = []string{...}`) instead of Header.Set, mirroring the
  existing WH-09 Allow-header pattern — Set's CanonicalMIMEHeaderKey lookup
  is pure overhead for these compile-time-constant, already-canonical keys.

  http.Request copy into one allocation (bundle = 320-352 B depending on
  size-class rounding) is, by construction, larger than the N=5 small
  independent closures (~39 B/alloc average) the old design allocated —
  trading allocation COUNT for allocation SIZE. This is the SAME structural
  trade-off already accepted as the codebase's DEFAULT (non-pooled) behaviour
  for the param-route dispatch hot path (reqBundle1/reqBundle2, params.go),
  which is far busier than the low-traffic redirect path. Two further levers
  exist but were deliberately NOT applied in this task: (a) gating a
  sync.Pool for redirectBundle behind the EXISTING Mux.PoolRequestBundle

  duplicating (even if only by re-invoking existing helpers) the

  which was judged not worth the risk for a bytes-only gain on a low-traffic
  path. Not pursued without explicit sign-off, per the "no unrequested
  architecture changes" and "ask when correctness/security trade-offs are
  ambiguous" working-agreement rules.

Concurrency evidence (rmp #250 WH-10 ABA fix)
--------------------------------------------------------------------------------
TestRedirect_ConcurrentUseVsConcurrentRedirects_NoRace (pre-existing test,
mux_redirect_middleware_test.go) is the adversarial stress test for the
lazyRedirect cache: 20 goroutines call Use() 15 times each (300 total)
concurrently with 200 goroutines each firing 150 redirects (30000 total),
under -race, then asserts a final redirect after everything settles invokes
exactly the full, 300-middleware chain.

First implementation attempt (plain "cache on first miss, Store
unconditionally" — the same pattern lazyNotFound/lazyMethodNotAllowed/
lazyOPTIONS already use) FAILED this test reliably (3/3 runs):
  final redirect invoked 293 / 268 / 248 middleware layers, want exactly 300
This is a genuine ABA race: a goroutine can read an old middleware snapshot,
build a handler from it, and Store it AFTER a newer snapshot's build already
published — silently reverting the cache to a stale, smaller middleware
count. Root-caused and fixed by tagging each middleware snapshot
(mwSnapshot) with a strictly increasing generation number assigned under
m.mu by Use(), and publishing lazyRedirect's cache with a CAS loop that
compares generations rather than relying on Store-call ordering (see the
lazyRedirect / mwSnapshot / lazyRedirectEntry doc comments in mux.go).

After the fix: PASS reliably, 5/5 runs under -race:

Aliasing fix (2026-09-25, task #250 follow-up, WH-05/WH-09) — MID-SETHEADER-1
class found process-wide, fixed, benchmarked
================================================================================
Host: AMD Ryzen 9 5900HX (16 threads), Go 1.27.0, Linux. go test -benchmem
-count=6, compared with benchstat.

DEFECT: middleware-security-reviewer's 2026-09-25 sprint 18 waste-hunt review
found and fixed MID-SETHEADER-1 in middleware/set_header.go — the WH-05
optimisation hoisted the single-element []string HEADER VALUE (not just the
string) into a variable shared across every request. http.Header.Set/Add/Del
never mutate an existing slice in place, so ordinary header manipulation
cannot observe this; but any downstream code indexing directly into the
slice (w.Header()[k][0] = ...) mutates the shared backing array in place,
corrupting the header for every OTHER request sharing that slice — past and
future — until process restart. Scanning the rest of the root package and
the middleware package for the same pattern found FOUR more sites, all
introduced by the same class of "hoist the []string, not just the string"
optimisation:

  response.go       JSON/XML/Text: one package-level []string per
                     Content-Type value, shared by EVERY request in the
                     process (widest blast radius in the root package).
  mux.go            lazyMethodNotAllowed: the per-Allow-key cached handler's
                     "Allow" slice shared by every request hitting that
                     cache entry; its default-handler branch ALSO shared two
                     package-level []string values (Content-Type,
                     X-Content-Type-Options) across every Allow-key AND
                     every Mux instance in the process.
  mux.go            lazyOPTIONS: the per-Allow-key cached handler's "Allow"
                     slice shared by every request hitting that cache entry.
  middleware/cors.go CORS(): seven per-instance closure variables
                     (Access-Control-Allow-Origin wildcard, -Credentials,
                     Vary, -Methods, -Headers, -Expose-Headers, -Max-Age)
                     shared by every request through that CORS() instance.
  middleware/no_cache.go NoCache(): five PACKAGE-LEVEL []string values
                     (Cache-Control, Pragma, Expires, Surrogate-Control,
                     X-Accel-Expires) shared across EVERY NoCache() instance
                     and every request in the process — the widest blast
                     radius found (wider than CORS's per-instance closures).

FIX: in every case, only the STRING is safe to hoist (it never changes);
the []string wrapping it must be allocated fresh on every request
(`w.Header()[k] = []string{constantString}`). This restores one allocation
per header write that the (unsafe) optimisation had eliminated — see
numbers below for the honest cost.
