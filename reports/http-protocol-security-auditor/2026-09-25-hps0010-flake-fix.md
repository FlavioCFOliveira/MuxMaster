# HTTP Protocol Security Audit — TestHPS0010 load-sensitivity fix

Date: 2026-09-25   Commit under audit: cbc4d0f5e2ac6e0d4d0cf79ed4eee399fc792f44 (branch feature/20-backlog-clearance)
Go: go1.27.0 linux/amd64   GOMAXPROCS: 16   rmp task: #269 (sprint 20)

## Scope

`TestHPS0010_RequestSmuggling_NetHTTPDefence` in
`reports/http-protocol-security-auditor/harness/http_protocol_audit_test.go`.
Nothing outside that single test function was in scope. No production file
(`mux.go`, `tree.go`, `response.go`, `handler.go`, `middleware/*`) was
touched — this was a test-harness defect, not a router defect.

## Defect

The test had been reported to fail once during a full-module
`go test -race -count=3 ./...` run and pass in isolation
(`reports/rpi5-benchmarks-2026-05-12.md`, "Pre-existing test failure").
A smuggling-defence assertion must not be load-sensitive: a flaky security
test is worse than no test, because a future genuine regression can hide
behind "oh, that one's just flaky."

## Root cause

`TestHPS0010` ran four smuggling-payload subtests against **one shared**
`muxmaster.Mux` / `httptest.Server` / `atomic.Bool` (`smuggledHit`), reset
with `smuggledHit.Store(false)` at the top of each `t.Run`.

The first payload (`CL.TE pipelining`) is *expected* to reach `/SMUGGLED` —
it sends a valid pipelined second request (`GET /SMUGGLED ...`) on the same
TCP connection right after the first. `rawHTTP()`, the raw-TCP client
helper, decides when to stop reading using a length/heuristic
(`sb.Len() > 200 && strings.Contains(sb.String(), "\r\n\r\n")`) rather than
parsing a real HTTP response boundary. Because the *first* response alone
(a 405 with `Allow`, `Content-Type`, `X-Content-Type-Options`, `Date`,
`Content-Length` headers) is already >200 bytes, the read loop can — and
under contention, does — return **before the server has even started
writing the second, pipelined response**.

`rawHTTP()`'s `defer conn.Close()` then fires immediately. But the client
closing its side does not abort request processing on the server side: the
full pipelined request was already delivered to the kernel in one `Write`
and buffered inside the server's per-connection reader, so `net/http`
continues parsing and dispatching it regardless of what the client does
next. The `/SMUGGLED` handler — and therefore `smuggledHit.Store(true)` —
can fire **after** the `CL.TE` subtest has already returned control to the
`for _, tc := range smugglePayloads` loop.

Under normal (unloaded) scheduling this residual goroutine runs in
microseconds, long before the next subtest's own `smuggledHit.Store(false)`
reset and round trip. Under the CPU contention of a full `-race -count=3
./...` run (or any other heavy concurrent load), Go's scheduler can delay
that residual goroutine arbitrarily. If its `Store(true)` lands *after* the
next subtest's reset but *before* that subtest's own
`hit := smuggledHit.Load()` check, the next subtest — one of `TE.CL`,
`TE.TE`, or the whitespace-header case, all of which assert `/SMUGGLED`
must **never** be reached — fails with:

```
CRITICAL HPS-2026-0010: Unexpected request reached /SMUGGLED handler!
```

...even though its own payload never triggered anything. This is a false
positive caused entirely by cross-subtest state sharing, not by any HTTP
framing weakness in MuxMaster or `net/http`.

### Empirical confirmation

Reproduced with the pre-fix code using 8 concurrent
`go test -race -run 'TestHPS0010|TestS8_H8_30' -count=15 -cpu=1,2,4,16`
invocations plus a concurrent background `go test -race -count=5 ./...`
for system-wide contention:

- 7 of 8 parallel invocations failed (`/tmp/hps_run_*.log`), each failure
  landing on `TE.CL`, `TE.TE`, or the whitespace case — **never** on
  `CL.TE` (which isn't asserted, consistent with the theory).
- A control run excluding `TestS8_H8_30_PanicHandlerDoublePanic` entirely
  (`-run 'TestHPS0010'` only) reproduced the same failure pattern at a
  similar rate (23 failures across 8×15 subtest runs), proving the panic
  noise from `TestS8_H8_30` is **not** a contributing factor — see
  "TestS8_H8_30 panic noise" below.
- Same failure pattern, same subtests, same absence of `CL.TE` failures —
  confirms the mechanism.

## Fix

Each subtest now gets its own `Mux`, `httptest.Server`, and `atomic.Bool`,
constructed inside the `t.Run` closure with `defer srv.Close()` local to
that closure:

```go
for _, tc := range smugglePayloads {
    t.Run(tc.name, func(t *testing.T) {
        m := muxmaster.New()
        var smuggledHit atomic.Bool
        m.GET("/SMUGGLED", func(w http.ResponseWriter, r *http.Request) {
            smuggledHit.Store(true)
            w.WriteHeader(200)
            w.Write([]byte("smuggled-reached"))
        })
        m.GET("/", func(w http.ResponseWriter, r *http.Request) {
            w.WriteHeader(200)
            w.Write([]byte("root"))
        })
        srv := httptest.NewServer(m)
        defer srv.Close()
        addr := srv.Listener.Addr().String()

        resp := rawHTTP(t, addr, tc.payload)
        // ... unchanged assertions ...
    })
}
```

This is not merely "add a mutex" — it removes the shared mutable state
entirely, which is the only way to make the guarantee unconditional rather
than probabilistic. `httptest.Server.Close()` blocks until all outstanding
requests on that server have completed (documented Go stdlib guarantee),
so even a still-in-flight pipelined request from a slow subtest is fully
drained before that subtest's closure returns — and it can only ever touch
*that subtest's own* `smuggledHit`, never a sibling's. Cross-subtest
contamination is now structurally impossible, not just unlikely.

No assertion was weakened: every subtest still asserts exactly what it did
before (`expectSmuggleFalse` semantics unchanged, same four payloads, same
CWE-444 / RFC 9112 analysis, same log messages). The `rawHTTP()` heuristic
read-loop was deliberately left as-is (see "Not fixed" below).

### Not fixed (and why)

`rawHTTP()`'s `sb.Len() > 200 && strings.Contains(...)` read-completion
heuristic is still imprecise — it does not guarantee the full response (or,
for `CL.TE`, both pipelined responses) has been read before returning.
This was tempting to "fix" by parsing real `Content-Length`/chunked
framing, but doing so is unnecessary for correctness once the shared-state
race above is removed: no subtest's *pass/fail* assertion depends on
`rawHTTP()`'s return value's completeness, only on the independent
`smuggledHit` flag, which is now provably isolated. Rewriting the read loop
would be a robustness nice-to-have, not a fix for this defect, and was left
out to keep the change minimal per the assertion-strength requirement.

## Verification

1. `go test -race -run TestHPS0010 -count=20 -v ./reports/http-protocol-security-auditor/harness/` — pass, both before and after the fix in isolation (the defect never reproduced in isolation, consistent with the original report).
2. Reproduced the flake on pre-fix code under load (see above) — 7/8 and (H8_30-excluded control) ~23/120 subtest-run failures.
3. Re-ran the *identical* stress workload against the fixed code — **0 failures** across 8×15 parallel runs plus a concurrent full-suite background load.
4. `go test -race -count=10 ./reports/http-protocol-security-auditor/harness/` — pass, 9.87s real.
5. Three consecutive full-module runs from repo root, `go test -race -count=3 ./...`:

   | Run | `http-protocol-security-auditor/harness` | Wall time (`real`) |

   | 2 | `ok` — 2.864s | 10m25.872s |

   All three runs exit non-zero (`FAIL`) overall, but in every run the

   `http-protocol-security-auditor/harness` itself is deterministic across
   all three runs.

## TestS8_H8_30 panic noise

`TestS8_H8_30_PanicHandlerDoublePanic` (same package,
`s8_hypotheses_test.go:443`) deliberately panics inside a handler and inside
a `PanicHandler` to verify `net/http`'s outer recovery catches both cases.
This produces expected stderr chatter (`http: panic serving ...` plus a
runtime stack trace) from Go's own `net/http` server logger — visible
proof, in `-v` output, that:

- `panichandler_panic_caught_by_nethttp` — a panic *inside* `PanicHandler`
  itself is still caught by `net/http`'s outer guard; the connection is
  closed (`EOF`), the server stays up.
- `panichandler_not_registered_no_recovery` — an unrecovered handler panic
  with no `PanicHandler` registered is likewise caught by `net/http`; the
  server stays responsive.

This is intentional, documented test behaviour (see the comments already in
that test), not a bug and not a contributor to the `TestHPS0010` flake: the
test uses `t.Parallel()`, its own dedicated `httptest.Server` per subtest
(already correctly isolated, unlike the old `TestHPS0010`), and the flake
was reproduced identically with `TestS8_H8_30` excluded from the run
entirely (see "Empirical confirmation" above). The noise in the original
failing CI log was two unrelated tests' stderr output interleaving in the
same package's log stream — cosmetically confusing, causally irrelevant.

## Escalation

The `reports/concurrency-security-auditor/harness` full-suite timeout found
during verification (reproducible 3/3, ~600s each time, pre-existing,
untouched by this diff) is outside `http-protocol-security-auditor`'s
mandate. Per the project's escalation paths this belongs to
`concurrency-security-auditor`: either the affected tests need a tighter
iteration/worker bound so they complete comfortably inside Go's default
10-minute per-package test timeout under full-suite `-race` contention, or
the CI invocation needs an explicit `-timeout` raised for that package.
Flagging for the maintainer/orchestrator to route; not actioned here per
scope discipline.

## Assertion-strength comparison

| | Before | After |
|---|---|---|
| Shared mutable state across subtests | 1 `Mux` + 1 `httptest.Server` + 1 `atomic.Bool` shared by all 4 subtests | Each subtest owns its own `Mux` + `httptest.Server` + `atomic.Bool` |
| Cross-subtest contamination | Possible under scheduler delay (proven, 7/8 and ~19% subtest-run failure rates under load) | Structurally impossible (isolated state; `httptest.Server.Close()` drains in-flight requests before the next subtest can start) |
| Payloads asserted | 4 (CL.TE pipelining, TE.CL, TE.TE, whitespace-header) | Unchanged — same 4, same bytes |
| `expectSmuggleFalse` semantics | Unchanged | Unchanged |
| CWE / RFC citations in failure messages | Unchanged | Unchanged |
| Determinism under `-race -count=3 ./...` × 3 | Failed at least once historically; reproduced 7/8 under stress | 0 failures across 3 full-module runs + dedicated stress reproduction (8×15 parallel + concurrent full-suite background load) |

No assertion was removed, loosened, or made conditional. The fix is purely
structural isolation of test state.
