### CL.TE "Smuggling" — Actually Valid HTTP/1.1 Pipelining
Input payload:
  POST / HTTP/1.1\r\n
  Host: localhost\r\n
  Content-Length: 5\r\n
  Transfer-Encoding: chunked\r\n
  \r\n
  0\r\n
  \r\n
  GET /SMUGGLED HTTP/1.1\r\nHost: localhost\r\n\r\n

Observed behaviour:
  Response 1: HTTP/1.1 200 OK  (for the POST /)
  Response 2: HTTP/1.1 200 OK  (for the pipelined GET /SMUGGLED)
  /SMUGGLED handler WAS called

Analysis:
  Go stdlib follows RFC 9112 §6.3: "Transfer-Encoding overrides Content-Length".
  Body is read as chunked ("0\r\n\r\n" = zero-length body). The Content-Length:5 is IGNORED.
  After the chunked body is consumed, "GET /SMUGGLED HTTP/1.1\r\nHost:..." is a valid
  pipelined second request — NOT a smuggled request.

  True CL.TE smuggling requires:
  - FRONTEND reads body using Content-Length (5 bytes → reads "0\r\n\r" as body)
  - BACKEND reads body using Transfer-Encoding (chunked → reads "0\r\n\r\n" as body = 0 bytes)
  This divergence is what makes smuggling work. When both frontend and backend are
  the SAME Go net/http server, there is NO divergence — hence NO smuggling.

Verdict: NOT a vulnerability in MuxMaster. Behaviour is correct per RFC 9112.
  The second request reaching /SMUGGLED is valid HTTP/1.1 pipelining.
