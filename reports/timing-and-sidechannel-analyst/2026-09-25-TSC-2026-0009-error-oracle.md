## Harness validity defect — root cause (confirmed 2026-09-25)

`buildErrorOracleMux()` registered `middleware.BasicAuth` with the root
`Mux.Use(...)`. `Mux.Use` is documented, by design, to wrap **every** handler
registered after the call **and** the mux's shared, lazily-built
NotFound/MethodNotAllowed handlers — see `mux.go`'s `Use()` doc comment and
the `lazyNotFoundPtr.Store(nil)` / `methodNotAllowedCache.Range(...Delete...)`
cache invalidation it performs on every call. That is intended behaviour for
cross-cutting middleware (logging, auth gates that must cover the whole
surface, etc.) — it is not itself a bug.

The effect on this harness: every unauthenticated request — including the
ones that should hit the router's own 404 (no route) or 405 (route exists,
wrong method) logic — was intercepted by `BasicAuth` before that logic ever
ran, and observably returned 401. The harness comment at the old
`error_oracle_test.go:89-93` asserted the opposite ("For 404/405, the mux
returns these before reaching the handler, so BasicAuth does NOT run"), which
was false for this construction. Confirmed by probe:

```
GET /no-such-route  auth=""                                      -> 401  (want 404)
GET /exists         auth=""                                      -> 401  (want 401 — this one was already correct)
DELETE /nonexistent-path auth=""                                 -> 401  (want 404)
DELETE /exists      auth=""                                      -> 401  (want 405)
```

So the defect affected **both** `TestTiming_ErrorOracle_404vs405` (both arms
401) and `TestTiming_ErrorOracle_404vs401` (the "404" arm was also 401). Only
`TestTiming_ErrorOracle_200vs401` and `TestTiming_ErrorOracle_Panic` were
unaffected, because neither test's "success" arm ever needed the mux-level
NotFound/MethodNotAllowed handler.

Consequence: the 404-vs-405 and 404-vs-401 numbers quoted from rmp #151 do
not measure what they claim. The accepted route-existence oracle class itself
remains correctly documented elsewhere (MM-2026-0026 / TSC-2026-0005, which
come from `route_existence_timing_test.go`, an unrelated harness that
compares a genuinely registered route against a genuinely unregistered one
on a mux with **no** auth middleware at all — that harness was never
affected by this defect).

## The fix (rmp #264)

### 1. `buildErrorOracleMux` now registers BasicAuth on a `Group`, not on the root `Mux`

```go
func buildErrorOracleMux() *muxmaster.Mux {
	r := muxmaster.New()
	g := r.Group("")
	g.Use(middleware.BasicAuth("test", map[string]string{"user": "password"}))
	g.GET("/exists", func(w http.ResponseWriter, req *http.Request) {
		w.WriteHeader(http.StatusOK)
	})
	g.POST("/exists", func(w http.ResponseWriter, req *http.Request) {
		w.WriteHeader(http.StatusOK)
	})
	return r
}
```

`Group.Handle` wraps only the specific handler registered through that group
(`g.mux.Handle(method, g.prefix+path, wrapMiddleware(handler, g.middleware))`
in `group.go`) and never touches the mux's NotFound/MethodNotAllowed
handlers. This keeps `/exists` authenticated (needed for the 401 and 200
arms) while leaving the mux's genuine, unauthenticated 404/405 dispatch paths
intact — which is exactly what these four tests are meant to compare. No
library code was changed; this is a harness-only fix, and it does not change
what is being measured (still: 404 dispatch vs 405 dispatch vs 401
auth-rejection vs 200 auth-success vs panic recovery).

### 2. A mandatory pre-measurement status check, shared by all 19 `TestTiming_*` harnesses (H-RECON-02)

Added `VerifyArmStatus` to `harness/timing.go`:

```go
func VerifyArmStatus(t *testing.T, arm string, handler http.Handler, buildReq func() *http.Request, want int) {
	t.Helper()
	req := buildReq()
	w := httptest.NewRecorder()
	handler.ServeHTTP(w, req)
	if w.Code != want {
		t.Fatalf("preflight failed for arm %q: want status %d, got %d — "+
			"harness setup does not exercise the intended code path; "+
			"any timing evidence collected from this arm would be invalid",
			arm, want, w.Code)
	}
}
```

Every one of the 19 `TestTiming_*` functions (`error_oracle_test.go` ×4,
`basic_auth_timing_test.go` ×2, `jwt_alg_confusion_timing_test.go` ×5,
`oauth2_cache_timing_test.go` ×2, `route_existence_timing_test.go` ×4,
`api_key_timing_test.go` ×2) now calls `VerifyArmStatus` once per arm
**before** the sample loop starts, and additionally checks `w.Code`/the
captured status on **every** sample inside the measurement loop itself
(`t.Fatalf` on the first mismatch), so a regression that only shows up after
warmup (e.g. state drift, cache expiry) is also caught — not just a
one-shot preflight. `route_existence_timing_test.go` gained a
`measureRouteWithStatus` helper (parallel to the pre-existing `measureRoute`)
that captures the status alongside each timing sample for this purpose.

`request_id_prng_test.go` (`TestPRNG_*`, not `TestTiming_*`) was out of scope
— it does not compare two timing arms.

### 3. Demonstration that a deliberately wrong arm now fails (not committed)

The "405" preflight expectation in `TestTiming_ErrorOracle_404vs405` was
temporarily changed from `http.StatusMethodNotAllowed` to
`http.StatusNotFound` (a deliberately wrong expectation) and the test run:

```
$ go test -tags timing -run TestTiming_ErrorOracle_404vs405 -v ./reports/timing-and-sidechannel-analyst/harness/
=== RUN   TestTiming_ErrorOracle_404vs405
    error_oracle_test.go:125: preflight failed for arm "405": want status 404, got 405 — harness setup
    does not exercise the intended code path; any timing evidence collected from this arm would be invalid
--- FAIL: TestTiming_ErrorOracle_404vs405 (0.27s)
FAIL
```

The test fails immediately at the preflight step, before any of the 150,000
timed samples are collected — confirming the guard does what it is meant to
do. The change was reverted immediately after this demonstration; it is not
present in the committed harness.

## Re-measurement with the fixed harness (valid evidence)

### Environment note

This re-measurement ran on a shared/virtualised sandbox VM, not the bare-metal
hosts used for the project's usual performance baselines (Apple M4 / Ryzen
9 5900HX in `CLAUDE.md`). Absolute ns/op figures below are therefore not
comparable to those baselines and are noisier (visible in the wider p99
tails); the relative comparisons within each triplicated run, and their
consistency run-to-run, are what matters for the oracle verdict.

### Commands

```
cd reports/timing-and-sidechannel-analyst/harness
go vet -tags timing ./...
go build -tags timing ./...
go test -tags timing -run 'TestTiming_' -v -timeout 600s .   # ×3, full suite
go test -tags timing -race -run 'TestTiming_ErrorOracle_Panic|TestTiming_ErrorOracle_404vs405' -v .
go test -tags timing -race -run 'TestTiming_JWT_AlgNoneVsHS256|TestTiming_Route_Param_vs_Static' .
```

### 404 vs 405 (`TestTiming_ErrorOracle_404vs405`, N=150,000/arm, triplicated)

| Run | 404 mean (ns) | 405 mean (ns) | Welch p | KS p | MWU p | \|mean diff\| (ns) |
|---|---|---|---|---|---|---|
| 1 | 2215.4 | 2545.4 | 0 | 0 | 0 | 270.15 |
| 2 | 2211.9 | 2541.2 | 0 | 0 | 0 | 244.50 |
| 3 | 2214.7 | 2500.7 | 0 | 0 | 0 | 248.68 |

Both arms confirmed 404 and 405 respectively on every one of the 450,000
samples across the three runs (per-sample `t.Fatalf` guard never fired).
Worst-case (largest) effect size: **270.15 ns** — classified LOW
("exploitable at LAN with ~100k requests") by the harness's own
`classifyOracle`. This supersedes the invalid 286 ns figure from rmp #151
(same order of magnitude and same LOW classification, coincidentally, but
the earlier number was never actually measuring 404 vs 405).

### 404 vs 401 (`TestTiming_ErrorOracle_404vs401`, N=150,000/arm, triplicated)

| Run | 404 mean (ns) | 401 mean (ns) | Welch p | \|mean diff\| (ns) |
|---|---|---|---|---|
| 1 | 2379.4 | 3000.3 | 0 | 594.53 |
| 2 | 2390.3 | 3027.9 | 0 | 562.38 |
| 3 | 2376.9 | 3073.5 | 0 | 567.14 |

Worst-case effect size: **594.53 ns** — classified LOW. This is a materially

## Full-suite re-run — all 19 `TestTiming_*` (H-RECON-02 acceptance check)

All 19 functions were re-run 3× (see commands above). 16 PASS with stable,
consistent figures run-to-run. Full log excerpts and the figures for
JWT (5), OAuth2 (2) and Route-existence (4) are in
`evidence/2026-09-25/full_run_{1,2,3}.log`. Notable, previously-accepted
figures re-confirmed within the same order of magnitude as SECURITY.md
("Accepted Timing Oracles"):

- JWT HS256 vs RS256 (mixed-family): ~25 µs mean diff, HIGH — consistent with
  TSC-2026-0003's documented conclusion (mixed-family alg-confusion oracle;
  operators must configure single-family `Algorithms`).
- OAuth2 cache active vs inactive: ~165 µs mean diff — larger than the
  143 µs figure in SECURITY.md TSC-2026-0007, but same conclusion
  (structural 200-vs-401 path-length difference, not a secret-value oracle);
  attributable to this sandbox's noisier network stack for the mock
  introspection server, not a regression.
- ECDSA zero-sig vs max-sig: ~1.2 µs mean diff — consistent with TSC-2026-0006
  (~1234 ns documented).
- Route existence (registered vs unregistered): ~970 ns mean diff —
  consistent with TSC-2026-0005 (923 ns documented; both far below the ~440 ns
  figure quoted in the "Route-Existence Timing Oracle (MM-2026-0026)" prose
  elsewhere in SECURITY.md, a pre-existing inconsistency between two
  SECURITY.md sections that is **not** part of this task's scope — flagged
  separately below, not fixed here).

**3 of 19 FAIL, unrelated to this defect and unrelated to this fix:**
`TestTiming_APIKey_HitVsMiss`, `TestTiming_BasicAuth_ValidVsInvalid`,
`TestTiming_BasicAuth_UserExistsVsNotExists` fail on every one of the three
runs with `t.Errorf`s such as "TIMING LEAK DETECTED" / "Effect size too
large". This is **pre-existing behaviour, byte-identical in this rmp #264
diff** — `git diff` on these two files touches only preflight/status-guard
additions, never the `if result.Leak { t.Errorf(...) }` assertion logic, and
`git show HEAD:.../basic_auth_timing_test.go` / `api_key_timing_test.go`
confirm the assertion was already there before this task started. The
measured effect sizes (953 ns / 88 ns / 307 ns) are close to the magnitudes
SECURITY.md already documents and accepts as architectural
(TSC-2026-0001: 890 ns; TSC-2026-0002: 61 ns; TSC-2026-0004: 1141 ns) — i.e.
these tests assert `t.Errorf` on statistical significance alone (any
`p < 0.01`), which at N=200,000 samples will reject the null for any
non-zero true effect, including the ones SECURITY.md explicitly accepts as
unfixable (Go's non-constant-time map lookup). This is a pre-existing
mismatch between the harness's pass/fail policy and the project's own
"Accepted Timing Oracles" doctrine, not a new regression, and out of this
task's requested scope (fixing the 404-vs-405/404-vs-401 harness only). It
is recorded as a new open item below for a maintainer decision, not
corrected here.

## New open items raised by this fix (not acted on — out of scope for rmp #264)

- **O-9 (new).** `TestTiming_APIKey_HitVsMiss`, `TestTiming_BasicAuth_ValidVsInvalid`
  and `TestTiming_BasicAuth_UserExistsVsNotExists` fail `t.Errorf` on every
  run in this environment, asserting statistical significance alone as a
  failure condition, which conflicts with SECURITY.md's "Accepted Timing
  Oracles" doctrine for the same three pairs (TSC-2026-0001, 0002, 0004).
  Pre-existing, unrelated to rmp #264. Needs a maintainer decision: either
  gate these on an effect-size threshold (as `TestTiming_APIKey_EmptyVsPresent`
  and the route-existence tests already do) or remove the `t.Errorf` and
  keep them as `t.Logf`-only regression evidence, consistent with the
  "accepted" classification.
- **O-10 (new).** SECURITY.md's "Route-Existence Timing Oracle (MM-2026-0026)"
  prose states "~440 ns" for a 404-vs-405 comparison, while TSC-2026-0005
  (same section family, "Accepted Timing Oracles") documents 923 ns for
  registered-vs-unregistered (200 vs 404, a different pair) from the same
  `route_existence_timing_test.go` harness. Neither number matches this
  report's newly-measured, harness-fixed 404-vs-405 figure (270 ns, from
  `error_oracle_test.go`, a different test). Three numbers for what reads as
  overlapping claims, from two different harnesses measuring two different
  pairs. Flagged for a maintainer decision on whether SECURITY.md's
  MM-2026-0026 prose should be reworded to disambiguate; not corrected here
  because it falls outside rmp #264's scope (that task named only the
  "Accepted Timing Oracles" section figures, which this defect does not
  contradict).
