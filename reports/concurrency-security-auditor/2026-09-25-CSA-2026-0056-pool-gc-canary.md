## Hypothesis

Per-request parameter storage could leak a value written by one request into
a later request (for example through a recycled backing array), exposing one
client's path parameters to another client.

## Method (from rmp task #25 and the harness)

Three canary tests in `h023_pool_canary_test.go` (build tag `race`):

| Test | What it does | Reported result (2026-05-07) |
|---|---|---|
| `TestPool_NoCrossRequestLeak` | A `/canary/:id` route writes a `__CANARY__` sentinel; concurrent requests to `/clean/:id` must never observe it | 800 K requests, 0 leaks |
| `TestPool_MultiTier_Isolation` | Exercises the 1-, 2- and 3+-parameter `reqBundle` tiers concurrently and checks each request sees only its own values | 2.4 M tier checks, 0 violations |
| `TestPool_GCPressure_Canary` | Forces `runtime.GC()` inside the handler under allocation pressure and checks parameter integrity | 0 corruptions |

The request counts above are quoted from the rmp task; they were not
re-counted for this write-up.

## Verdict (2026-05-07)

At the audited commit no `sync.Pool` was used for `Params`; each `reqBundle`
was freshly allocated per request and its lifetime was managed by the GC.
Cross-request contamination was therefore structurally impossible in that
design, and the canary confirmed it empirically under `-race`. The rmp task
asked for the canary to be kept as a regression guard for any future pooling
refactor.

## Coverage gap (open)

The 2026-05-07 verdict ("zero pool contamination risk because no pool is
used") no longer describes the whole of HEAD. Two opt-in pooling modes have
since been added:

- `Mux.PoolRequestBundle` (Opt O13): recycles `reqBundle` through a `sync.Pool`.
- `Mux.PoolFastParams` (Opt O9): recycles the `Params` slice of `HandleFast` routes.

The canary does not set either flag. A search of every `*_test.go` file in the
repository (excluding `.claude/` and `competitor/`) found these flags used
only in `bench_test.go` and `reports/perf-lab-2026-09-24/harness/`
(benchmarks and layout checks), not in any contamination or isolation test.
This gap is filed as hypothesis H-RECON-01 in `reports/overview/findings.md`
for the maintainer to schedule. No test was added as part of this write-up.
